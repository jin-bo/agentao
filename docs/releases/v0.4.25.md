# Agentao 0.4.25

A **patch release** for one defect that 0.4.24 shipped: a sub-agent started
while `/skills disable` or `/skills enable` was running could activate every
skill the user had disabled.

## What was wrong

0.4.24 made a disabled skill impossible to activate, and made
`/skills disable` and `/skills enable` re-read the config file under a lock
and adopt the set it holds. Adopting emptied the in-memory disabled set and
then refilled it. A sub-agent copies that set when it starts, without a lock,
and a background sub-agent does so from its own thread — so one started
between those two steps copied an empty set:

- Every skill the user had disabled could be activated by that sub-agent's
  model.
- For the sub-agent's whole run. Disabling again on the parent does not reach
  a copy the sub-agent already holds.
- Any `/skills disable` or `/skills enable` opened the window — including one
  naming an unrelated skill, one that changed nothing, and one that answered
  "Unknown skill", because the file is read and adopted before that answer.

The file lock was not involved: it protects the file, not the set in memory.

## The fix

The set now grows before it shrinks. It first becomes the union of the old
and the new set, then the new set, so every state a sub-agent can copy still
holds every name that either side disables.

The regression test does not depend on thread timing. It derives a sub-agent
after every change made to the set and checks that none of them can activate
a skill that stays disabled, across five transitions: disable, enable, a
no-op, an unknown name, and a config another writer changed. All five fail
on the 0.4.24 ordering.

This closes that window only. The skill manager is still not built for
concurrent writers.

## Who is affected

Anyone on 0.4.24 who disables or enables skills while a sub-agent may be
starting. In the interactive CLI that means a background sub-agent. An
embedded host that calls `SkillManager.disable_skill()` or `enable_skill()`
from another thread can hit it with either kind.

Versions before 0.4.24 do not have this window, but in those versions a
disabled skill could be activated by name anyway.

## Also in this release

- The skills guide and the configuration reference now say that a sub-agent
  copies the disabled set when it starts: a disable made while one is running
  applies to the next sub-agent, not to that one.

## Compatibility

No API, configuration or wire change. The `skills_config.json` format is
unchanged, and nothing needs migrating.
