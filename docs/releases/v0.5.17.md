# Agentao 0.5.17

This release is about following a sub-agent from a host. A sub-agent run can
now be joined to the parent's call that started it, every run has its own
session id, and a new opt-in switch puts the sub-agent's own tool calls and
permission decisions on the parent's `events()` stream. It also fixes an MCP
call that could still be sent after its caller gave up, and gives a bare HTTP
`413` one compaction and one retry. Two changes behave differently on upgrade; see
[Behaviour changes](#behaviour-changes).

## Behaviour changes

- **New schema versions: host events v3, replay 1.6.** `SubagentLifecycleEvent`
  gains `parent_tool_call_id`. The model is closed
  (`additionalProperties: false`), so the field is a new schema version: the
  host event snapshot is now `docs/schema/host.events.v3.json` and replay is
  `schemas/replay-event-1.6.json`. The field is always sent, as `null` when
  unset, so a validator built from `host.events.v2.json` or
  `replay-event-1.5.json` rejects every `SubagentLifecycleEvent`. **Move a
  validator to the new file.** Both old files are frozen as published. Code
  that reads the models, or ignores unknown keys, needs no change.
- **`/clear`, `/new` and `/compact` refuse an argument** (#574). They take
  none, and used to drop any they were given, so `/clear just the
  conversation` still wiped every memory and `/compact focus on X` ran an
  ordinary compaction. A non-blank argument now prints a notice and the
  command does nothing else. A blank argument runs as before, and
  `/clear all` stays an alias for `/clear`.

## Following a sub-agent from a host

- **`child_task_id` on foreground transport events** (#578). Each foreground
  run puts one id on its `AGENT_START`, its `AGENT_END`, and every child event
  it forwards (`TURN_START`, `TOOL_CONFIRMATION`, `TOOL_START`, `TOOL_OUTPUT`,
  `TOOL_COMPLETE`). The run's `SubagentLifecycleEvent` carries the same id.
  Pair a run's transport events by this id, not by the agent name. It is an
  additive field, and `schema_version` stays `1`.
- **`parent_tool_call_id` on `SubagentLifecycleEvent`** (#580). Every phase of
  a run carries the `tool_call_id` of the parent's `ToolLifecycleEvent` for
  the `agent_*` call that started it, foreground and background, so a host
  joins the call and the run without pairing them by order. It is `None` only
  for a run not started through the tool executor.
- **`child_session_id` on every run** (#583). It was always `None`. The id is
  now minted before `spawned`, and the sub-agent's own host events use it as
  their `session_id`. The lifecycle events keep the parent's `session_id`, so
  `events(session_id=<parent>)` still sees every run start and end. A run that
  ended before its sub-agent was built keeps the id it reserved, and that
  session has no events.
- **Opt-in relay: `Agentao(..., relay_subagent_events=True)`** (#584). Every
  host event a sub-agent publishes (its `ToolLifecycleEvent`s and
  `PermissionDecisionEvent`s) is republished, unchanged, on the parent's
  `events()` stream, in the run's `child_session_id`. Off by default, so a
  host that counts every `ToolLifecycleEvent` as the parent's sees no change.
  - Subscribe once, with `session_id=None`, before the run starts. That
    subscriber gets `spawned`, then the run's child-session events, then its
    terminal event, when the agent runs off the event loop (`arun()`, or
    `chat()` on another thread). A subscriber filtered to the parent's session
    sees no relayed event.
  - The synchronous `chat()` on the loop thread that `events()` is bound to
    gives no ordering guarantee. Use `arun()` there.
  - Replay does not record relayed events: a replay file has the same rows
    with the switch on or off. `HostReplaySink` takes a new `skip_session=`
    argument for this, and `start_replay()` wires it.

Design: `docs/design/subagent-event-channels.md` in the repository.

## Fixes

- **An MCP tool call given up while it waits for an OAuth token refresh is no
  longer sent** (#571). A call that timed out or was cancelled while its
  request waited for a shared refresh, or for one after a `401`, still reached
  the server once the refresh finished, so a side-effecting tool ran although
  the model was told the call failed. The request is now answered locally
  without being sent. This holds on mcp 2.x (Streamable HTTP and SSE). On
  mcp 1.x the request is still sent.
- **A bare HTTP `413` gets one compaction and one retry** (#572). A provider
  that answers an oversized request with an uninformative `413` (GitHub
  Copilot: `failed to parse request`) used to end the turn with a plain error.
  It now runs one full compaction and retries once. If that does not succeed,
  the provider's error is returned. It never reaches minimal history, and no
  image is removed because of the `413` alone.
