# Agentao 0.4.24

A **sub-agent release**. A sub-agent was built as a near-copy of its parent,
and the copy had quietly diverged on almost everything that matters: which
tools it could run, whose MCP servers it talked to, which database it wrote
memories into, whose permission rules applied to it, which skills it could
see, and what a cancel looked like from outside. Most of these were found by
probing the running system rather than by reading it, and each one was a
different way the same sentence — "a sub-agent behaves like its parent,
narrowed" — turned out to be untrue.

The headline:

- **A sub-agent executed tools it was never shown.** It was shown its
  definition's `tools:` list and executed against every tool its construction
  had registered. A background `codebase-investigator`, described as
  read-only, could write files. `complete_task` always failed with "Tool not
  found", and that error text came back to the parent as the sub-agent's
  answer.
- **A sub-agent applied no permission rules at all.** The planner held a
  `None` engine, so a call the user's rules deny asked the parent instead —
  and a headless parent approved it. A background sub-agent was built with no
  callbacks, which gave it a transport that approves every confirmation.
- **A sub-agent launched its own MCP servers** on every spawn, ignoring the
  ones a host had given the parent in code, and nothing closed them.
- **A sub-agent's compaction wrote into the parent's memory database** — its
  session summary resurfaced in the parent's next prompt as an earlier
  session, and its crystallized proposals landed in a review queue no bulk
  clear reaches.
- **A cancelled sub-agent was reported as a failure**, but only if it had
  already started. The same user action, two terminal states, decided by
  timing.
- **A sub-agent had an empty skill catalogue**, so `activate_skill` was a tool
  that could only answer that the skill is unknown.
- **A tool name was repaired by similarity.** `read_file` and `write_file` are
  as close as a typo, so a sub-agent denied `read_file` wrote with
  `write_file`.

## Tools a sub-agent can run

There is now one registry for what a sub-agent is shown and what it executes:
the parent's live registry at spawn, narrowed to the definition's `tools:`
list. Built-ins arrive as the child's own instances bound to the parent's
filesystem and shell; MCP tools are the parent's, over the parent's
connections; agent tools and plan tools are left out.

Which is which comes from the origin recorded at registration, never from the
class — a host's `WebSearchTool(backend=...)` registered under `web_search` is
a host tool, and the first version of this fix took it for the built-in and
handed the sub-agent a default instance whose searches went somewhere else.

A host tool reaches a sub-agent only by declaring `copies_to_subagents` on the
tool object, and then as one shallow copy made per spawn. Every way the
declaration can be got wrong — a bare `def` where a `@property` was meant, a
`__copy__` that answers with `self`, a declaration that raises — leaves the
tool out with a warning rather than in.

Tool-name repair no longer dispatches by similarity. It normalises padding,
case, separators, camelCase and a trailing `Tool` suffix, and answers only
when one of those reproduces an offered name exactly. Guarding the fuzzy pass
closed one input class at a time while leaving the mechanism that produced
them; the pass is gone.

## Skills

A sub-agent now gets a `child_view()` of the parent's live skill manager —
the same catalogue and disabled set, an empty `active_skills`. Derived rather
than re-scanned, because a re-scan reproduces neither a plugin's in-memory
entries nor a catalogue a host injected.

Four separate defects let a disabled skill come back:

- `activate_skill` never consulted `disabled_skills`; it resolved the name
  through `available_skills`, where a disabled skill was still present.
- `reload_skills()` intersected the disabled set with what the scan had just
  found and persisted the result, so one `/skills reload` dropped a disable
  for a skill that was merely not discoverable right now.
- `_save_config` overwrote the whole file with the set this process held, and
  that set was filled exactly once at construction — so a second process's
  disable, or a hand edit, was gone at the next `/skills disable`.
- A `disabled_skills` value that was not an array either crashed the CLI at
  startup or expanded a bare string to its characters.

The config write is now a read-modify-write of one name, with the read and the
write inside one lock, swapped in via a temp file.

## Memory

A sub-agent is built on a transient store of its own, so its session summaries
and its crystallized proposals are discarded with it. The read side goes with
it deliberately: a sub-agent reads no memories and is briefed by the parent's
recent messages instead. Its `save_memory` still writes through the parent's
manager, so it can save a long-term memory it cannot read back.

`MemoryManager.wipe_all()` is new, and is what `/clear` and `/memory clear`
call. It returns a result whose `ok` is the success signal rather than the
counts: `clear_all_session_summaries()` answers 0 both for "nothing to delete"
and for a delete that failed, so the summaries are confirmed by reading the
store back. Two things it does not promise, both now documented: the review
queue, and erasure — the memories half is a soft delete, so the rows keep
their content in the file.

## MCP

The client manager ran its event loop inside whichever caller reached it
first, so two MCP calls in one model response lost one of them to `This event
loop is already running`. The loop now runs on the manager's own thread and
callers submit to it, so concurrent calls run at the same time over one
session. Each connection lives in one owner task that opens and closes it,
which is what the SDK's cancel scopes require and what the "Attempted to exit
cancel scope in a different task" warning was reporting. `disconnect_all()` is
final and bounded.

## Also in this release

- `/clear` and `/new` no longer let a background agent report into the
  conversation they start, and neither does a sub-agent take notifications
  addressed to the top-level conversation.
- An ACP-loaded session gets its active skills back; both entry points read
  the persisted list and then dropped it.
- A corrupt session file is answered as the client's error, not the server's.
- A scope downgrade with no user store says so instead of being silent.
- A transient memory store survives being written from another thread, and a
  file-backed store no longer loses one of two concurrent saves of the same
  key.
- The Windows suite runs in parallel, and agentao's own artifacts stop being
  written into the repository root during tests.

## Compatibility

- **`SubagentLifecycleEvent`:** a sub-agent cancelled while running now
  arrives as `phase="cancelled"` with `error_type=None`. It used to arrive as
  `phase="failed"` with `error_type="incomplete:cancelled"`. A host that told
  cancels from crashes by parsing that string reads the phase instead. The
  record moves in lockstep and keeps the partial result.
- **Sub-agents and host tools:** a host tool reaches a sub-agent only if its
  object declares `copies_to_subagents`. An undeclared tool is absent by name,
  and the built-in it replaced does not reappear underneath it.
- **Tool names:** a misspelling that the similarity pass used to repair now
  returns the existing tool-not-found error, and the model re-issues the call.
- **Skills:** `/skills activate X` on a disabled skill now fails where it used
  to be obeyed. Run `/skills enable X` first.
- **Memory:** hosts wiping memory should call `MemoryManager.wipe_all()` and
  check `result.ok`. `clear()`, `clear_all_session_summaries()` and
  `session_summaries_remain()` are unchanged.
- Records already in `background_tasks.json` keep their old
  `failed`/`incomplete:cancelled` rows; nothing migrates them.
