# Agentao 0.5.6

This release is about background sub-agents: what happens after one
finishes. It has three themes:

- **The CLI picks up a finished background agent's result by itself.** When
  a background sub-agent finishes while the CLI waits at an empty prompt, the
  CLI now runs one turn so the main agent reads the result. Before, the
  result sat in a queue until you typed something.
- **A parent can wait for a result inside one turn.**
  `check_background_agent` takes `wait_seconds`. This is the path for ACP
  clients, which start every turn themselves and cannot be woken.
- **Background-agent views show this conversation.** The status bar,
  `/agent status`, the dashboard and the model's own listing no longer show
  tasks from earlier conversations or earlier runs, and the record file no
  longer grows without bound.

What prompted it: a parent launched three background agents and waited with
`sleep 300` shell calls. The third identical call tripped the doom-loop
guard and ended the turn. The last agent finished 18 minutes after that;
all three results were read two and a half hours later, when the user typed
`continue`.

No public method was removed. A few changes can affect an existing setup.
Read the next section before upgrading.

## Check this before upgrading

**1. `agentao run` no longer offers background sub-agents.** Its factory now
passes `bg_store=None`, so `run_in_background` is not in the agent tool
schema and `check_background_agent` / `cancel_background_agent` are not
registered. A one-shot run exits when its turn ends, and background workers
are daemon threads, so their work could be cut off. Foreground sub-agents are
unchanged. A run spec or prompt that asks for background agents now gets
sub-agents run in the foreground, inside the turn.

**2. The interactive CLI can start turns you did not type.** Automatic
continuation is on by default. It runs only at an empty prompt, never in plan
mode or with images staged, and stops after 3 wakes in a row until you enter
a line. It also applies to agents you started with `/agent bg`. To turn it
off:

```json
{
  "background_agents": {
    "auto_wake": false
  }
}
```

in `.agentao/settings.json`. Only a JSON boolean is honoured; another value
is reported and read as `true`.

**3. Listings show this conversation by default.** `/agent status`,
`/agent dashboard` / `/agents`, and the model's
`check_background_agent(agent_id='')` now list this conversation's tasks
plus any still running. Add `--all` to the CLI commands for the full
history. `/agent status <id>` and `check_background_agent(agent_id=<id>)`
still read any task by its id.

**4. Older finished records are dropped.** At startup and at each launch,
`.agentao/background_tasks.json` keeps at most 50 finished records from
earlier conversations and runs, the newest by finish time. This
conversation's records and running tasks are never dropped. If you relied on
that file as a permanent log, copy it elsewhere.

## Waking an idle CLI

A finished background agent queues a notice. The queue is read only on the
parent's next request, so a parent whose turn had ended used to sit at the
prompt until you typed. Now, when a new notice is queued and the prompt is
idle, the CLI prints `⟳ background agent finished — continuing` and runs one
turn. That turn reads every notice queued so far. Typing wins: if you start
typing just as a notice arrives, the prompt stays open.

The runtime still never starts a turn itself. The CLI does it as a host. An
embedded host can do the same from the terminal `SubagentLifecycleEvent` of a
background task (`parent_task_id` set); `docs/reference/host-api.md`,
*Continuing after a background sub-agent*, has the recipe. The event is a
cue, not proof that a notice is still queued: a running turn may already
have read it.

The launch message and the `run_in_background` description now tell the
model to carry on or end its turn, not to wait with `sleep` or repeated
status checks.

## Waiting inside a turn

`check_background_agent(agent_id, wait_seconds=N)` blocks until that agent
finishes, for at most `N` seconds (0 to 1800; the default 0 answers at once,
as before), and returns its result in the same turn.

- **Cancelling the turn ends the wait, not the agent.** Ctrl+C, ACP
  `session/cancel`, or cancelling the token passed to `chat()` end the wait
  within half a second. Only `cancel_background_agent` stops the agent.
- **A wait that runs out says so** and tells the model not to repeat it. The
  doom-loop guard is unchanged.
- **A long wait reports progress** once a minute through the normal tool
  output (`TOOL_OUTPUT`, ACP `tool_call_update`).
- **Two waits in one parallel batch run one after the other**, because both
  calls go through the same tool instance.

The 1800-second bound is provisional. It has not been checked against an ACP
client's own prompt-turn timeout; a client that gives up first ends the turn
from its side.

**Ctrl+C in a parallel tool batch** now cancels the turn before the batch
waits for its other tools. Before, a tool that was waiting could hold the
interrupt for its whole wait.

## What the CLI shows

The status bar used to show every background task the project had ever
recorded: tasks finished before `/new` or `/clear`, and in a fresh CLI every
task in `background_tasks.json`, including ones cut off by the previous exit
and marked failed. It now shows this conversation's tasks and any still
running, and it no longer reads that file once a second.

The model's listing had the same problem and called it "this session", so in
a new session the model could see the previous run's failed agents as its
own. It now uses the same scope.

An embedded host can read either view from the store:

```python
from agentao.agents.bg_store import BackgroundTaskStore

store = BackgroundTaskStore()
store.register("a1", "worker", "summarize the docs")
store.mark_running("a1")
store.update("a1", status="completed", result="done")
store.start_new_conversation()

print([t["id"] for t in store.list()])          # ['a1'] — history
print([t["id"] for t in store.list_current()])  # []     — this conversation
```

## Upgrading

```bash
pip install -U agentao
```

Check the four items at the top if you:

- use `agentao run` with prompts or specs that launch background agents;
- would rather the interactive CLI did not start turns on its own;
- read `/agent status` or the model's agent listing for history;
- keep `.agentao/background_tasks.json` as a record.
