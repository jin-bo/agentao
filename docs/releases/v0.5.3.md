# Agentao 0.5.3

A third wire protocol: **OpenAI's Responses API**, selected with
`api_format="openai-responses"`. It uses the `openai` SDK Agentao already
installs, so there is no new dependency. Nothing is removed and nothing needs
migrating.

## Turning it on

The Responses API is selected like the other two protocols. It is **never
inferred** from a URL, a provider name or a model name.

```bash
# .env — the same base URL Chat Completions uses
OPENAI_API_KEY=sk-...
OPENAI_BASE_URL=https://api.openai.com/v1
OPENAI_MODEL=gpt-5.4
OPENAI_API_FORMAT=openai-responses
```

```python
agent = Agentao(
    working_directory=workdir,
    api_key=api_key,
    base_url="https://api.openai.com/v1",
    model="gpt-5.4",
    api_format="openai-responses",   # keyword-only; sub-agents inherit it
)
```

`/provider` and ACP's `provider_resolver` switch between blocks on different
wires, and they switch the protocol along with the credentials.
`examples/openai-responses-wire/` is a runnable sample. Its offline smoke test
runs the real SDK over a scripted socket.

## What differs on this wire

**Requests are stateless.** Agentao sends `store: false` and no
`previous_response_id`, and it sends the whole history every time. Compaction
rewrites Agentao's history, `/clear` wipes it and replay replays it. A
conversation kept on the provider's side would drift away from all three.
`agent.messages` keeps the same OpenAI-style shape on every wire, so session
files, replay and compaction are unchanged.

**A reasoning model's reasoning carries over from one request to the next.**
Because the provider keeps nothing, earlier reasoning reaches the next request
only if Agentao sends it back:

- Every request asks for `reasoning.encrypted_content`.
- Each reasoning item is kept whole on its assistant message, under
  `openai_reasoning_items`, and goes back ahead of its turn.
- An item that has no encrypted content is not kept. Under `store: false` the
  provider has nothing stored under that id.
- These items are dropped, the same way as Anthropic's signed thinking, on a
  model or provider switch, on `/resume` and on ACP `session/load`.
- If an endpoint rejects the field, Agentao resends that request once without
  it. After that it never sends the field or the items again.

**`/thinking <level>` writes `reasoning.effort`.** This API rejects a
top-level `reasoning_effort` on every request, so the level goes into the
`reasoning` object instead:

- Other keys you put in `reasoning`, such as `summary`, are left alone.
- A `reasoning_effort` carried in from another wire is removed.

Reasoning summaries are the only reasoning text this API shows. They stay off
unless you ask for them:

```bash
LLM_EXTRA_BODY='{"reasoning": {"summary": "auto"}}'
```

**A few smaller differences:**

- Tools are sent with `strict: false`. Strict is the API's default for a
  function tool, and strict mode rejects a schema that does not list every
  property as required. Agentao's own tools and MCP servers' tools don't.
- `LLM_MAX_TOKENS` is sent as `max_output_tokens`, raised to the API's minimum
  of 16 if it is lower.
- `temperature` is sent until a model rejects it, the same as on Chat
  Completions.
- An `incomplete` response counts as a truncation. The runtime already refuses
  to run tool calls from one.
- A failure inside a stream that started with HTTP 200 is raised as an error.
  The SDK hands it over as an ordinary event, and reading only the events you
  expect would end the turn as an empty answer. `server_error` and
  `rate_limit_exceeded` are retried. A quota error is not.

## Moving a session between wires

A Responses function call has two ids, a `call_id` and an item id (`fc_…`).
History has one slot for both, so Agentao stores them together as
`call_id|fc_…`. This matters when a session moves to Chat Completions:

- As api.openai.com issues them, that combined id is 83 characters long.
- Chat Completions allows 64. That was observed on the live API:
  `string_above_max_length`, "Expected a string with maximum length 64".
- Because the id stays in history, every request after a switch would fail
  with the same 400.

The Chat Completions adapter now sends such an id as its `call_id`. It changes
only the copy it sends; history keeps the original, so the session can switch
back to Responses. Two further rules:

- **Only combined ids are rewritten.** Every other id is sent unchanged,
  whatever its length. A request that contains none is sent exactly as before.
- **When two calls share a `call_id`, a hash suffix keeps them distinct.** The
  hash does not depend on the order the calls appear in. If compaction removes
  one of the pair, the other goes back to its bare `call_id`.

## Cache writes on the OpenAI wires

`openai` 3.x reports how many input tokens were written to the cache, as
`cache_write_tokens`. On both OpenAI wires that count now reaches
`cache_creation_tokens`, `usage_snapshot()` and `agentao run`'s `usage`. On
`openai` 2.x, or on an endpoint that does not report it, the count stays 0 as
before.

Agentao sets no upper bound on its `openai` dependency, so a fresh install
gets 3.x. The test suite was run on 2.24.0 and on 3.16.2.

## Tested against real endpoints

Agentao was run against two real endpoints: api.openai.com (`gpt-6-astra`,
`gpt-4.1-mini`) and an OpenAI-compatible Aliyun gateway
(`deepseek-v4.1-flash`). About twenty small requests in total. These all
worked:

- tool-call round trips;
- encrypted reasoning carried back across three requests;
- a history moved to Chat Completions and continued there.

The runs also showed a few things the documentation does not:

- **The live output order is reasoning → message → function call.** Agentao
  sends a turn back in that same order.
- **One pairing rule was not enforced.** pi-mono, another open-source
  implementation, records that the API rejects an `fc_` id sent without its
  reasoning item. On api.openai.com with `store: false`, all four combinations
  were accepted. Agentao still sends the `fc_` id only beside its reasoning,
  since that costs nothing.
- **The gateway behaves differently.** It issues `msg_…` ids for every item,
  function calls included, and sends reasoning as plain text with no encrypted
  content. So on that gateway reasoning is shown but not carried to the next
  request, which is the correct behaviour.
- **Some models skip reasoning at lower effort.** At `low` and `medium` effort,
  `gpt-6-astra` often produced no reasoning item at all.

Two cases never came up on either endpoint, so they are still untested:

- an endpoint rejecting `include`. Three common phrasings of that error are
  recognised.
- an `error` event whose `code` is empty. It is treated as permanent, so it is
  not retried.

The full record is under *Live results* in `docs/design/llm-api-adapters.md`.

## Upgrading

```bash
pip install -U agentao
```

No API was removed or changed. `api_format="openai-responses"` is new. An
unknown `api_format` still fails at startup, and `gemini-api` still does too,
because it is not implemented yet. The one behaviour change on an existing
path is a history id of the form `call_id|fc_…` being rewritten when it is
sent to Chat Completions. Only the Responses wire creates ids in that form.
