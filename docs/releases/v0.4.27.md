# Agentao 0.4.27

A **one-change release**: the available-skills catalogue goes back into the
system message. 0.4.26 had moved it to the request-only tail, where it turned
out to be the tail's largest item — re-sent uncached on every request, every
tool iteration included. No API changed and nothing needs migrating.

## The skills catalogue is in the cached prefix again

0.4.26 split the model's instructions in two: a system message that stays
byte-identical across a session, and a volatile tail that rides each request.
The catalogue went to the tail with the other volatile blocks. It was volatile
for one reason only: it listed the *inactive* skills, so every activation
rewrote it.

It now lists **every enabled skill that has a description, active or not**,
sorted, and sits in the system message ahead of `<memory-stable>`. Activating or
deactivating a skill leaves the system message byte-identical. What activation
changes is the active-skills block, which stays in the tail — and that block is
also how the model learns which catalogue entries are already active. The
catalogue's closing instruction now says to call `activate_skill` when a skill
matches *and is not already active*.

Measured in the agentao repository with 14 skills on disk: the system message
goes from about 2.7k to about 5.2k tokens, and the idle tail from about 2.5k to
empty. **These are local token estimates of request shape, not billed figures.**
No billed cache-hit comparison against a real endpoint has been run, for this
release or for 0.4.26; compare against your own deployment before reading it as
a saving.

### What invalidates the prefix now

The catalogue changes only when the *enabled set* does — enable, disable,
install, reload. Those events already rewrite the `activate_skill` tool's
`skill_name` enum in the tools block, so they were rebuilding the cached prefix
anyway. The move adds no new invalidation, **with one exception**: a reload that
picks up an edited `description` or `when-to-use` rewrites the catalogue and not
the enum, which carries names only.

One timing difference. The catalogue is now read when the system message is
built — per turn, again when the active set or the memory version changes, and
after a full compaction — rather than per request. The tools block, enum
included, is serialized once per turn. A skill disabled mid-turn can stay listed
until the next turn; `activate_skill` still refuses it.

The catalogue sits ahead of stable memory because it changes less often: on an
endpoint with a token-prefix cache, a `save_memory` rebuilds from the memory
block on and the catalogue stays cached. With the opt-in `cache_control`
markers the system message is sent as a single text block, so there a
`save_memory` re-writes all of it whichever order the two are in.

### What did not change

- The catalogue still renders only for an agent that has the `activate_skill`
  tool — not under `disable_tools`, an `enabled_tools` allowlist that omits it,
  or a sub-agent definition whose `tools:` list does.
- An active skill's **body** is still in the tail, and is now the tail's large
  item: about 4.1k tokens per request for one skill in this repository.
  `/skills deactivate` when you are done with one. Whether bodies belong in the
  prefix depends on when in a session skills get activated, which has not been
  measured.

## One posture note

For hosts that load third-party or plugin skills: a skill's `description` and
`when-to-use` are system-role text again, as they were before 0.4.26, rather
than sitting inside the tail's `<system-reminder>` wrapper. They are not
neutralized or stripped on the way in. A skill's body was always model-visible
instruction text by design, so this widens nothing an installed skill could not
already do — but it is the placement to know about when auditing what reaches
the system message.

## Who needs to do something

- **Hosts or tests that read the available-skills catalogue out of
  `_build_volatile_tail()`.** It is in `_build_system_prompt()` again. Both are
  private.
- Everyone else: nothing.

## What comes next

0.5.0 is planned as a removal release: `agentao.harness`, `agentao.session`
and the eight legacy callback kwargs on `Agentao(...)`, all of which have
emitted a `DeprecationWarning` through 0.4.x. Run your test suite on this release with
`python -m pytest -W error::DeprecationWarning`; a clean run covers those three.
Two further 0.5.0 changes cannot show up that way — `project_root` becomes
required on the `agentao.embedding.sessions` functions, and `Agentao(...)` takes
only its first five parameters positionally — so if you call either, pass those
arguments by keyword now. Both spellings already work on 0.4.27.

## Compatibility

No public API added, removed or changed, and no configuration migrated. The
model-visible instructions are the same text as in 0.4.26, with the catalogue
listing active skills too and sitting in the other message.
