# Agentao 0.5.2

A small release that finishes what 0.5.1 started. 0.5.1's notes ended its usage
section with two admissions — *"a request that failed mid-stream may go
uncounted, and a background sub-agent can finish after `agentao run` has
written its envelope."* This release closes the first, and closes the part of
the second that was a defect rather than a fact. Nothing is removed and
nothing needs migrating.

## A sub-agent's cost, on the event that says it finished

**`SubagentLifecycleEvent` has a `usage` field.** On a terminal phase it is a
`SubagentUsage` — `prompt_tokens`, `completion_tokens`, `cache_read_tokens`,
`cache_creation_tokens`, the same four quantities under the same names as
`agentao run`'s `usage`. `prompt_tokens` is the whole input and the two cache
counts are parts **of** it. It covers a run that failed or was cancelled too:
its requests were made whatever came of them.

`usage` is `None` on `spawned`, on a run cancelled before it started, and on
one whose construction raised. `None` means *not read*, never *zero*.

**The order was wrong on the background path, and is fixed.** 0.5.1 added a
sub-agent's usage to its parent's totals from the `finally` that closes it. For
a background sub-agent that ran *after* the record was updated and the terminal
event published — so a host that read `agent.llm.total_prompt_tokens` from its
`completed` handler got a total that still left the run out. Usage is now
settled first, once, on every terminal path. The foreground path already had
this order.

One consequence to get right: **do not add `event.usage` to a total you read
after the event.** It is already in there. The field exists so a cost can be
attributed to the sub-agent that incurred it, not so it can be summed again.

Also new:

| Surface | New |
|---|---|
| `agentao.host` | `SubagentUsage` |
| `LLMClient` | `usage_snapshot()` — the four totals from one locked read |
| `BackgroundTaskStore` record | `usage` — the same dict; `tokens` stays what it always was, a local estimate of the final history's size |
| `host.events.v1`, replay 1.2 / 1.3 schemas | the `usage` property, counts `minimum: 0` |

A background record recovered from a file written before 0.5.2 has no `usage`
key at all — read it with `.get("usage")`.

## A stream that fails part-way is still counted

The session totals were added after the stream consumer *returned*, so an
attempt that raised — an `error` event inside the stream, a dropped connection —
added nothing. On the `anthropic-messages` wire that was a whole request's
input going uncounted, because `message_start` states the full input count in
the stream's first event.

The adapter now records usage on its way out either way, and `LLMClient` counts
it once per attempt. Three things this does and does not mean:

- It is what the server **reported**, not a claim about what it billed.
- A failed attempt and the retry after it are **two requests**, and both count.
  What cannot happen is one attempt counted twice.
- **Chat Completions is unchanged in effect.** That wire states usage only in
  its last chunk, so a stream that dies before it has nothing to keep, and
  nothing is invented for it.

`chat()` — the summarizer's path, which is a stream on the Anthropic wire too —
counts a failed attempt the same way. `LLM_CALL_COMPLETED` on the error path
still carries no counts.

## What is still true about `agentao run`'s `usage`

It is a **snapshot, read when the envelope is written.** `agentao run` does not
wait for background sub-agents: one that finishes in time is included, one still
running is not, and nothing revises the envelope afterwards. That is a fact
about a run that ends, not a defect, and the docs now say it in those words. A
host that needs a per-sub-agent figure reads `SubagentLifecycleEvent.usage`.

## Measured, and left alone

0.5.1 promised that a cancelled task is not *continued* after the Models API
lookup, and said the lookup itself is not interruptible. This release measured
how long that can hold a cancel — real SDK, real sockets, cancel sent 0.1 s
after the request:

| The models route… | cancel → return | generation request sent |
|---|---|---|
| accepts the connection, then says nothing | 4.9 s | no |
| is at an unroutable address | 4.9 s | no |
| sends one byte every 4 s | 23.9 s (as long as it keeps trickling) | no |

The promise holds in every case: nothing was sent after the cancel. The wait is
bounded at the 5-second per-phase timeout against an endpoint that is dead or
unreachable. It is **not** bounded against one that trickles, because the
timeout applies per read — that needs the lookup moved to its own thread, which
was considered and not done: there is no report of a real endpoint behaving that
way, and the cost is a thread in every embedded host. It will be revisited on
evidence.

## Design docs

`docs/design/README.md` listed nine plans as live backlog that had shipped —
among them `enabled_tools` (0.4.9), indexed as a draft, and the ACP modes/plan
work (0.4.12), indexed as a proposal. They are now under *Landed contracts*.

One sentence was untrue and is corrected in place, with its date: the
permission-hardening plan said the command floor already follows `rm -rf`
through variable indirection using `bashlex`. Nothing in agentao imports
`bashlex`, and measured against the floor, `rm -rf /` and `timeout 5 rm -rf /`
are denied while `D=/; rm -rf $D`, `D=rm; $D -rf /` and `X=-rf; rm $X /` pass.
**This release documents that gap; it does not close it.** The floor is a last
line against the unrecoverable, not a sandbox: the permission mode and rules
still sit in front of it. Closing the gap is variable propagation, which needs
its own design first.

## Upgrading

```bash
pip install -U agentao
```

No API was removed or changed. `SubagentLifecycleEvent.usage`, `SubagentUsage`
and `LLMClient.usage_snapshot()` are additions. The event models are
`extra="forbid"`, so a host that **re-validates** serialized events against a
pinned copy of the 0.5.1 model or schema will reject the new key — validate
against the schema of the version you run.
