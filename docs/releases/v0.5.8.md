# Agentao 0.5.8

This release is about the [ACP Registry](https://agentclientprotocol.com/registry),
from both sides:

- **Agentao can be installed from the Registry.** A client that launches it
  through `uvx` has no `.env` to edit, so Agentao now supports ACP
  **Terminal Auth**: `agentao --login` asks for a provider and key and saves
  them to `~/.agentao/llm.json`, and a session with no provider answers
  `auth_required` instead of failing later.
- **Agentao can add agents from the Registry.** `/acp registry search` and
  `/acp registry add` turn a Registry entry into an `npx` / `uvx` server in
  `.agentao/acp.json`, and `/acp login` runs an agent's terminal login.

Testing the second half against real Registry agents found three defects in
the ACP client, fixed here: a missing credential could mark a server fatal,
a server that crashed on start took two minutes to report it, and `/acp`
showed a server waiting for a login as `failed`.

No public method was removed. One change affects existing ACP server setups.
Read the next section before upgrading.

## Check this before upgrading

**On the ACP server, a project's `.env` now supplies only LLM settings.**
One `agentao --acp` process serves sessions from several projects. It used to
load each session's `<cwd>/.env` into the shared process environment without
overriding, so the first session's keys, model and endpoint stuck for every
later session that set the same variables. Now each `session/new` /
`session/load` resolves its LLM settings from three layers, highest first:
the server's launch environment, the project `.env`, and
`~/.agentao/llm.json`. Nothing is written into `os.environ`, and no `.env` is
searched for above `cwd`.

Settings other code reads from the environment no longer come from the
project `.env` on this path. Move them into the ACP client's launch `env`
block:

- MCP `${VAR}` expansion in `mcp.json`;
- `JINA_API_KEY`, `BOCHA_API_KEY`;
- `GITHUB_TOKEN`;
- `AGENTAO_WEB_FETCH_*`.

A few rules decide which layer wins. The provider is chosen first: the
highest layer that names one, else `OPENAI`. Only that provider's variables
are read after that. An API key's presence never chooses the provider, so an
`OPENAI_API_KEY` exported for another tool does not override a DeepSeek
login. The API key, base URL and wire format are taken together from the
highest layer that sets the key. A key with no base URL beside it leaves the
URL missing (`auth_required`) rather than borrowing a lower layer's, so it is
never sent to the gateway a login named.

The interactive CLI, `agentao run`, `build_from_environment()` and a host
that injects its own `agent_factory` / `provider_resolver` are unchanged.

## Installing Agentao from the Registry

A Registry client launches Agentao as:

```bash
uvx 'agentao[cli]@0.5.8' --acp
```

To configure it, run the login in a terminal:

```bash
uvx 'agentao[cli]@0.5.8' --login
```

It asks for provider, API key (hidden), base URL, model and wire protocol,
and writes `~/.agentao/llm.json` with mode `0600`. The wire protocol defaults
to `anthropic-messages` for ANTHROPIC and `openai-completions` otherwise, and
is always saved. The command exits `0` only when a complete configuration is
on disk; Ctrl-C exits `130`, end of input or a failed save exits `1`.

A client that declares Terminal Auth (`clientCapabilities.auth.terminal`, or
the legacy `_meta["terminal-auth"]`) is offered one `terminal` auth method in
`initialize`, with `args: ["--login"]`, and runs the login for you. Other
clients get `authMethods: []` as before. Either way, a session with no
provider answers `auth_required` (`-32000`) naming the missing fields, and
for a client without Terminal Auth also a login command that works without
`agentao` on `PATH`. The server reads `llm.json` on every `session/new`, so a
login done while it runs takes effect without a restart.

`agentao --acp` and `agentao --login` now refuse arguments they do not know
(exit `2`). A mistyped flag used to start a server that read stdin to end of
input and exited `0`.

## Adding Registry agents to the CLI

```text
/acp registry search claude
/acp registry add claude-acp            # server name defaults to the id
/acp send claude-acp "summarize README.md"
```

`add` shows the agent, its version and launch command, and writes nothing
until you confirm. It writes an ordinary `acp.json` entry with
`autoStart: false` and `startupTimeoutMs: 120000`, since the first launch
downloads the package. The entry works at once, without restarting the CLI.
Nothing is launched until the first `/acp send` or `/acp start`.

What it accepts:

- `npx` and `uvx` entries; Node.js or uv must already be installed. An entry
  that offers both uses `npx`. Binary-only entries are refused.
- A package spec that pins the entry's own version: `name@1.2.3`,
  `@scope/name@1.2.3`, `name==1.2.3`, with optional uv `[extras]`.
- Not a name that is already configured, not an invalid existing `acp.json`,
  and not `env` values containing `$` (which `acp.json` would expand). Other
  entries are kept and the file is replaced atomically.

An agent without credentials answers `auth_required`, and `/acp` lists it as
`needs login`. If it offers a `terminal` auth method:

```text
/acp login claude-acp
```

runs that login in your terminal, the way the ACP spec describes: the
server's own command, arguments and `cwd`, with the method's `args` appended
and its `env` applied. The login runs as a foreground job, so hidden input
and Ctrl+C reach it and not the CLI, and a cancelled or failed login is ended
together with anything it started. Exit status `0` restarts the server and
connects again. While a login runs, a turn on that server gets `SERVER_BUSY`.
Other auth method types are not run; authenticate outside Agentao and
`/acp restart <name>`.

Agentao removes its own provider keys from an ACP server's environment, as it
does for MCP servers and hooks. An agent that reads its key from the
environment therefore does not see your shell's key; log in, or give the key
to that server in its `env` block (`"GEMINI_API_KEY": "${GEMINI_API_KEY}"`).

We ran this against the live Registry. pi-acp went through the whole flow:
`auth_required`, `/acp login`, restart, a session and a first turn.
claude-acp and dirac also offer terminal logins but open a session without
credentials. Two `uvx` agents in the Registry, fast-agent 0.10.1 and
minion-code 0.1.44, did not start at all for reasons of their own.

## ACP client fixes

- **`auth_required` no longer makes a server fatal.** It counted toward the
  handshake-failure streak, so sending twice before logging in marked the
  server fatal and replaced "requires authentication" with "call
  restart_server". It now keeps its `-32000` code, carries
  `details["auth_required"]` and `details["auth_methods"]`, and is left out of
  the streak.
- **A server that exits before answering fails the request at once.** The
  requests still waiting sat out their whole timeout, so a Registry agent that
  crashed on start took 120 s to report a timeout. They now fail when the
  server's output closes, with `server closed its output while waiting
  for '<method>'`. `/acp logs <name>` shows why it exited.
- **`startupTimeoutMs` now applies.** It bounds the wait for `initialize`
  (never less than the previous 30 s). It was parsed and documented but
  never used, so a first-run download slower than 30 s failed the handshake.
- **`/acp` and `/acp status`** show `needs login` instead of `failed` for a
  server waiting for a login. A successful `/acp login` clears the recorded
  `auth_required` error. `/acp status` re-checks the process, so a server
  that died mid-turn is no longer shown `ready`.
- **Windows:** a bare `npx` / `uvx` command is resolved against the server's
  `PATH`, since without a shell Windows does not find the `.cmd` shim. A
  cancelled or failed login is ended through a job object, which also catches
  what a runner started.

## For embedded hosts

Each step of the CLI's Registry flow is a separate call, so a host decides
whether to write the file, register the server or start it:

```python
from pathlib import Path

from agentao.acp_client import ACPManager
from agentao.acp_client.config import add_server_entry
from agentao.acp_client.registry import entry_to_server_config, fetch_registry, find_agent

project = Path(".")
agent = find_agent(fetch_registry(), "claude-acp")
entry = entry_to_server_config(agent)
print(entry.command_line)                      # shown to the user before writing

config = add_server_entry("claude-acp", entry.config, project)
manager = ACPManager.from_project(project, terminal_auth=True)
print(manager.server_names, manager.needs_login("claude-acp"))
```

- `ACPManager(..., terminal_auth=)` and `ACPManager.from_project(...,
  terminal_auth=)`, default `False`: declare Terminal Auth to servers. Declare
  it only when you can run a login in a terminal.
- `ACPManager.add_server(name, config)` registers a server on a running
  manager, stopped.
- `ACPManager.auth_methods(name)` returns what the server advertised at its
  last `initialize`. `ACPManager.needs_login(name)` is true while its last
  session setup answered `auth_required`.
- `ACPManager.reserve_for_login(name)` is a context manager that holds the
  server for a login: turns on it get `SERVER_BUSY`, and it refuses while a
  turn is active.
- `agentao.acp_client.auth` has `is_auth_required`, `terminal_auth_methods`
  and `build_terminal_login_command`, which builds the spec's argv / env /
  cwd for a method.
- `build_from_environment(resolved_llm=)`, keyword-only, takes LLM settings
  the caller already resolved; with it the factory loads no `.env` and reads
  no LLM setting from `os.environ`. `discover_llm_kwargs()` and
  `resolve_provider_name()` take an optional `env` mapping to read instead of
  `os.environ`.

## Upgrading

```bash
pip install -U agentao
```

Check the section at the top if you run `agentao --acp` and keep non-LLM
settings (MCP `${VAR}` values, web-tool keys, `GITHUB_TOKEN`) in a project
`.env`.
