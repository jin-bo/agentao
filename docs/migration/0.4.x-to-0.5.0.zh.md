# 从 0.4.x 迁移到 0.5.0

**状态：** 0.5.0 版本的现行迁移指南。
**依据的清单：** `docs/design/0-5-0-removal-checklist.zh.md`。

0.5.0 是一个**移除版本**。它没有新增任何你必须采纳的东西 —— 唯一的新增
`anthropic-messages` 线路协议是 opt-in 的（见「没有变的」）。§1–§3 里的每一项在
0.4.x 期间都一直在发 `DeprecationWarning` —— `agentao.harness` 自 0.4.2 起，其余
自 0.4.5 起。**§4 和 §5 从未告警过**，因为那种调用方式本身并没有被弃用：即使你的
0.4.x 运行一条警告都没有，这两节也要读。

---

## TL;DR —— 我受影响吗？

在最后一个 0.4.x 上把警告当错误跑一遍你自己的测试：

```bash
python -m pytest -W error::DeprecationWarning
```

干净通过，说明 §1、§2、§3 与你无关。然后 grep 那两项用这种方式查不出来的：

```bash
grep -rnE "(save_session|load_session|load_session_record|persist_agent_session|list_sessions|delete_session|delete_all_sessions)\(" your_package/
grep -rnE "Agentao\(" your_package/     # 找位置参数超过五个的调用
```

| § | 什么 | 在 0.5.0 上的症状 | 0.4.x 是否告警过 |
|---|---|---|---|
| 1 | `agentao.harness` | `ModuleNotFoundError` | 是，自 0.4.2 |
| 2 | `agentao.session` | `ModuleNotFoundError` | 是，自 0.4.5 |
| 3 | `Agentao(...)` 的八个回调 kwarg | `TypeError: unexpected keyword argument` | 是，自 0.4.5 |
| 4 | `agentao.embedding.sessions` 的 `project_root` | 点名 `project_root` 的 `TypeError` | **否** |
| 5 | `Agentao(...)` 第五个之后的位置参数 | `TypeError: takes … positional arguments` | **否** |
| 6 | `Agentao` 上的私有属性 | `AttributeError` | 否（私有） |
| 7 | 提示词里的 “Reasoning Requirement” 段 | 无 —— 提示词变短了 | 否 |

---

## 1. `agentao.harness` → `agentao.host`

别名包已删除。改名是机械的 —— 模块路径和每个符号里的 `harness` → `host`、
`Harness` → `Host`：

| 0.4.x | 0.5.0 |
|---|---|
| `agentao.harness`（以及 `.events` / `.models` / `.projection` / `.protocols` / `.replay_projection` / `.schema`） | `agentao.host`（子模块同名） |
| `HarnessEvent` | `HostEvent` |
| `HarnessToolEmitter` / `HarnessPermissionEmitter` / `HarnessSubagentEmitter` | `HostToolEmitter` / `HostPermissionEmitter` / `HostSubagentEmitter` |
| `HarnessReplaySink` | `HostReplaySink` |
| `harness_event_to_replay_kind` / `harness_event_to_replay_payload` | `host_event_to_replay_kind` / `host_event_to_replay_payload` |
| `replay_payload_to_harness_event` | `replay_payload_to_host_event` |
| `export_harness_event_json_schema` / `export_harness_acp_json_schema` | `export_host_event_json_schema` / `export_host_acp_json_schema` |

其余名字在两条路径下本来就拼写相同。对象还是同一批对象，所以事件载荷、schema、
快照都没有任何变化。

如果你是在源码检出上原地升级，请删掉残留的 `agentao/harness/__pycache__` 目录：
Python 会把一个没有 `__init__.py` 的目录当成空的命名空间包导入，于是
`import agentao.harness` 看起来成功了，而每一句 `from agentao.harness import …`
都会失败。`pip` 安装不受影响。

## 2. `agentao.session` → `agentao.embedding.sessions`

```python
# 0.4.x
from agentao.session import save_session, load_session

# 0.5.0
from agentao.embedding.sessions import save_session, load_session
```

这个 shim 除了转导出之外只做了一件事：你不传 `project_root` 时，它替你填
`Path.cwd()`。这个兜底现在在任何地方都不存在了 —— 见 §4，它同样适用于你。

## 3. `Agentao(...)` 的八个回调 kwarg

`confirmation_callback`、`step_callback`、`thinking_callback`、
`ask_user_callback`、`output_callback`、`tool_complete_callback`、
`llm_text_callback` 和 `on_max_iterations_callback` 不再是参数。agent 上同名的
属性（`agent.confirmation_callback` 等）也一并没有了。有两条路，第一条只改一行。

**保留你的回调，包一层。** `build_compat_transport` 接受同样的八个名字，而且
没有被弃用 —— 它就是受支持的迁移面：

```python
from agentao import Agentao
from agentao.embedding.compat import build_compat_transport

agent = Agentao(
    working_directory=project_dir,
    transport=build_compat_transport(
        confirmation_callback=my_confirm,
        llm_text_callback=my_print,
        step_callback=my_step,
    ),
)
```

**或者改用事件流。** 一个 `on_event` 处理函数顶替五个展示类回调；三个交互类回调
各有自己的关键字：

| 回调 | `SdkTransport(...)` |
|---|---|
| `confirmation_callback` | `confirm_tool=` |
| `ask_user_callback` | `ask_user=` |
| `on_max_iterations_callback` | `on_max_iterations=` |
| `step_callback` | `on_event=` —— `TURN_START`、`TOOL_START` |
| `thinking_callback` | `on_event=` —— `THINKING` |
| `output_callback` | `on_event=` —— `TOOL_OUTPUT` |
| `tool_complete_callback` | `on_event=` —— `TOOL_COMPLETE` |
| `llm_text_callback` | `on_event=` —— `LLM_TEXT` |

见 `developer-guide/zh/part-4/3-sdk-transport.md`。

完全不传 `transport=` 时，agent 拿到的仍是 `NullTransport`：静默，并且对每一次
确认都放行。这个默认行为没有变。

`ToolRunner(...)` 也不再接受那四个自 Transport 协议落地以来就一直被忽略的回调
kwarg。它是内部运行时类；只有你自己构造它时才相关。

## 4. `agentao.embedding.sessions` 的 `project_root` 变为必填 —— **从未告警过**

在 0.4.x，七个入口的签名都是 `project_root: Optional[Path] = None`，而 `None` 的
含义是进程的当前目录。直接调用 `agentao.embedding.sessions` 的人同样如此，不只是
走 `agentao.session` shim 的人 —— 而且没有任何警告，因为这种调用本身没有被弃用。

在 0.5.0 它是必填的，并且**显式传 `project_root=None` 同样被拒绝**（`TypeError`），
而不是悄悄解析成 cwd。要紧的不只是 `save_session`，还有 `delete_all_sessions`：
一个自己的根目录变量没赋值的宿主，过去会一声不吭地读、写、删除另一个项目的会话。

| 函数 | 0.5.0 签名 |
|---|---|
| `save_session(messages, model, active_skills=None, session_id=None, *, project_root)` | 仅限关键字 |
| `persist_agent_session(agent, session_id=None, *, project_root)` | 仅限关键字 |
| `load_session(session_id=None, *, project_root)` | 仅限关键字 |
| `load_session_record(session_id=None, *, project_root)` | 仅限关键字 |
| `list_sessions(project_root)` | 必填 |
| `delete_session(session_id, project_root)` | 必填 |
| `delete_all_sessions(project_root)` | 必填 |

**一律用关键字传 `project_root=`，七个都能用。** 前四个之所以是仅限关键字，是因为
它排在可选参数后面；过去按位置传它的调用（`load_session(sid, root)`）现在会抛错。

如果你要的确实就是 cwd，就明说：`project_root=Path.cwd()`。

## 5. `Agentao(...)` 只接受五个位置参数 —— **从未告警过**

那八个回调在位置上是*夹在*其他参数中间的：

```
api_key, base_url, model, temperature, max_tokens,
confirmation_callback, max_context_tokens, step_callback, …,
permission_engine, on_max_iterations_callback, transport, plan_session
```

直接删掉它们，`max_context_tokens`、`permission_engine`、`transport`、
`plan_session` 就会整体前移，一个仍把回调传在第六位的调用会被悄悄绑到
`max_context_tokens` 上。所以 `max_tokens` 之后的一切现在都是仅限关键字，那种调用
会在写下它的地方得到 `TypeError`。如果你本来就用关键字传这四个 —— 文档里的每个
示例都是这样 —— 对你没有任何变化。

## 6. 从 `Agentao` 上移除的私有属性

都带下划线前缀，从来不是契约的一部分；列在这里是因为有些测试套件会伸手去拿：

| 已移除 | 改用 |
|---|---|
| `agent._replay_config` | `agent.replay_manager.config` |
| `agent._replay_recorder` | `agent.replay_manager.recorder` |
| `agent._replay_adapter` | `agent.replay_manager.adapter` |
| `agent._host_replay_sink` | `agent.replay_manager.host_replay_sink` |
| `agent._emit_context_compressed(...)` | `agentao.replay.observability.emit_context_compressed(agent, ...)` |
| `agent._emit_session_summary_if_new(prev)` | `agentao.replay.observability.emit_session_summary_if_new(agent, prev)` |
| `agent._latest_session_summary_id()` | `agentao.replay.observability.latest_session_summary_id(agent)` |

从未挂过 replay 的 agent（没传 `replay_config=` 的裸 `Agentao(...)`）上，
`agent.replay_manager` 是 `None`。旧的 `_replay_config` 在这种情况下返回一个禁用的
默认值；现在请自己判断 `None`。

过去靠*打补丁*替换 `agent._emit_context_compressed` 来捕获事件的测试，应改为从
transport 上捕获 —— 线上载荷的键是 `type`、`reason`、`pre_msgs`、`post_msgs`、
`pre_est_tokens`、`post_est_tokens`、`duration_ms`。

**没有移除**，尽管 0.4.5 的发布说明曾把它们列给 0.5.0：`agent.start_replay()`、
`agent.end_replay()`、`agent.reload_replay_config()` 以及构造参数
`replay_config=`。CLI 和 ACP 服务器在每个会话里都会调用它们；它们保留。

## 7. 提示词里的 “Reasoning Requirement” 段已退役

在 0.5.0 之前，当且仅当构造函数收到 `thinking_callback=` 时，系统提示词会多出一段
`=== Reasoning Requirement ===`。没有别的东西会设置那个开关：走 `transport=` 的
宿主从来没有这一段，其中包括按建议用 `build_compat_transport` 包了
`thinking_callback` 的宿主，也包括 agentao 自己的 CLI、ACP 服务器和
`agentao run` —— 自 2026-04-04 起一直如此。kwarg 没有了，这一段也随之退役，而不是
反过来对每个从未有过它的宿主打开。

如果你过去传了 `thinking_callback=` 并且想把这条指令要回来，把它放进项目的
`AGENTAO.md` —— 那是系统提示词的第一段：

```
=== Reasoning Requirement ===
Before any tool call that modifies state, runs a shell command, or is part of a multi-step investigation, write 2-3 sentences:
- Action: What tool you are calling and with what input.
- Expectation: What you expect to find or what the result should confirm.
- If wrong: What you will do if the result contradicts your expectation.
Skip this preamble for trivial read-only lookups (single read_file, list_directory, glob). Be specific and falsifiable when you do write it.
```

`THINKING` 事件不受影响 —— 它承载的是模型的推理输出，从不依赖这一段。

## 没有变的

- `agentao.embedding.compat.build_compat_transport` —— 有意保留。
- `agentao.tool_runner`（`agentao.runtime.tool_runner` 的旧导入路径）—— 那是另一个
  shim，不在本次发布范围内。
- 事件载荷、ACP schema 快照、配置文件、CLI。
- 线路协议。0.5.0 可以原生说 Anthropic 的 Messages API
  （`{PROVIDER}_API_FORMAT=anthropic-messages`、`api_format=`），但只在你明说时才会：
  不根据 URL、provider 名或模型名做任何推断，现有部署仍走 Chat Completions。每个安装都会
  看到的只有一处：**新增核心依赖** `anthropic>=1.6.0`（连带 `docstring-parser`）；它是惰性
  导入的，默认线路上从不加载。见 `docs/reference/configuration.zh.md` §2。
- 两处宿主可能注意到、但无需处理的增量：ACP 的 `provider_resolver` 可以多返回一个可选的
  `api_format` 键（不带即 Chat Completions，与以前完全一样）；`get_usage_stats()` 多了一个
  `reported_limit` 键。`/thinking` 在 Chat Completions 上不变；在新线路上它写的是
  `output_config.effort`，而不是 `reasoning_effort`。
